# CH5 공부노트

> 💡HTTP와 WebSocket 차이점
> 
1. 편지와 전화통화의 차이
- HTTP (지난주): "편지"와 같습니다. 클라이언트가 서버에 요청(Request)을 보내야만, 서버가 응답(Response)을 줍니다. 용건이 끝나면 연결을 바로 끊어버리죠. 실시간으로 계속 데이터를 주고받기에는 매번 연결을 맺고 끊어야 해서 네트워크 낭비가 심하고 느립니다
- WebSocket (이번주): "전화통화"와 같습니다. 처음에 한 번 전화를 걸어 연결을 맺어두면, 끊을 때까지 파이프라인이 계속 열려 있습니다. 클라이언트가 묻지 않아도 서버가 먼저 데이터를 보낼 수 있고, 양방향으로 지연 없이(실시간) 데이터를 주고받을 수 있습니다. 실시간 멀티플레이어나, AI 모델이 실시간으로 분석한 좌표를 언리얼로 스트리밍할 때 필수적
2. 핸드셰이크(Handshake)란?
- 처음 연결을 시도할 때는 웹소켓도 HTTP 방식을 빌려 씁니다. "우리 이제부터 HTTP 말고 WebSocket으로 실시간 통신하자!"라고 합의를 보는 과정인데, 이를 핸드셰이크라고 부릅니다. 이 과정이 성공적으로 끝나면 본격적으로 실시간 데이터 파이프가 열리게 됩니다

> 💡WebSocket의 구조와 동작 원리
> 
1. WebSocket의 생명주기
- 1단계: 핸드셰이크 (Handshake - HTTP로 첫인사)
    - 클라이언트(언리얼 엔진)가 서버에게 HTTP 형태로 "우리 이제 웹소켓으로 통신할래?" 라고 제안합니다.
    - 서버가 수락하면 상태 코드 101 (Switching Protocols)을 반환하며 HTTP 연결이 웹소켓 연결로 업그레이드됩니다.
- 2단계: 연결 유지 (Open - 파이프라인 개통)
    - 성공적으로 연결되면 양쪽을 잇는 전용 도로(터널)가 뚫립니다.
    - 이때부터는 연결을 명시적으로 끊기 전까지 터널이 계속 유지됩니다.
- 3단계: 양방향 데이터 전송 (Message - 데이터 핑퐁)
    - 가장 중요한 단계입니다. 클라이언트가 요청하지 않아도, 서버가 원할 때 언제든 데이터를 쏠 수 있습니다.
    - 데이터는 보통 텍스트(주로 JSON)나 바이너리(0과 1의 이진 데이터) 형태로 가볍게 전송됩니다. HTTP처럼 무거운 헤더(Header)가 매번 붙지 않아 압도적으로 빠릅니다.
- 4단계: 연결 종료 (Close - 파이프 닫기)
    - 클라이언트나 서버 중 한 곳에서 "이제 그만 통신하자"고 신호를 보내면 터널이 닫힙니다.
    - 게임이 종료되거나, 레벨을 이동할 때 직접 닫아주는 로직이 필요합니다.

> 💡HTTP vs WebSocket (왜 게임/AI 연동에 필수인가?)
> 
| 구분 | HTTP (Polling) | WebSocket |
|---|---|---|
| 작동 방식 | 클라이언트가 0.1초마다 "데이터 있어?" 계속 물어봄 | 파이프를 열어두고 서버가 "데이터 왔어!" 하고 그냥 줌 |
| 서버 부하 | 질문마다 연결/해제를 반복하여 트래픽 낭비 극심 | 최초 1회 연결만 하므로 가벼움 |
| 통신 방향 | 단방향<br>(클라이언트 → 서버 요청 필수) | 양방향<br>(서버 → 클라이언트 먼저 전송 가능) |
| 활용 예시 | 날씨 API, 환율 정보, 일회성 DB 저장<br>(W4 내용) | 실시간 AI 위치 트래킹, 멀티플레이어 동기화, 채팅<br>(이번 주 목표) |
